# 測試結果與實機驗證清單

> 原則：已驗證與尚未驗證的項目分開列出。所有「已驗證」都是對**真的 App**（不是模擬伺服器）實際連線、截圖量測的結果。

## 1. 自動測試環境

開發環境是 Linux 雲端主機，**無法操作你的 Mac**；所有 macOS 測試都在 GitHub Actions 的 macOS 機器上執行（每次推送程式自動跑）：

| 項目 | 版本 |
| --- | --- |
| macOS | 15.7.9（24G830），Apple 晶片（arm64）虛擬機 |
| Xcode / Swift | Xcode 16.4 / Swift 6.1.2 |
| Node.js（測試工具） | 22.23.2 |
| 螢幕 | 虛擬顯示器 1024×768（沒有 Apple TV、沒有實體投影機） |
| 瀏覽器（端對端測試） | Google Chrome（模擬 iPhone 13 螢幕） |

App 本身支援 macOS 12 以上，同時包含 Apple 晶片與 Intel 版本（universal binary）。

### 2.5 壓力測試：200 支手機（`tests/loadtest.mjs`）
每支模擬手機使用不同的 IP（127.0.0.2～127.0.0.201），使用與手機網頁完全相同的協定。

| 情境 | 結果 |
| --- | --- |
| 200 支手機同時連線 | 200 成功、0 失敗，全部完成 101 ms |
| **一般互動**：200 人在線，全場平均每 3 秒有人送一則（45 秒） | 16 則全部顯示；回條 p50 1.6 ms / p95 5.5 ms；**送出到上螢幕 p50 6.3 ms / p95 12.9 ms** |
| **同一瞬間 200 人一起送** | 15 則進入顯示佇列、184 則收到「目前彈幕太多，請稍後再送」、1 則因重複被擋；回條 p95 34.6 ms |
| **極端：每個人每 6～20 秒都在送（約 16.6 則/秒，60 秒）** | 994 則中 28 則排入、966 則即時告知稍後再送；回條 p95 1.8 ms、最大 20.6 ms；排入的訊息在 30 秒內上螢幕（p50 26.2 s） |
| 測試結束仍連線 | 200 / 200 |
| App 資源（整段壓力測試） | **記憶體最高 56.6 MB；CPU 平均 1.2%、最高 10.8%** |

解讀：
- 伺服器處理本身在毫秒等級；**真實環境的延遲主要取決於 Wi-Fi**（一般 5～50 ms），1 秒內送達的目標有充足餘裕。
  以上數據是同一台機器上的連線，未包含 Wi-Fi，請以實機測試為準。
- 「同時最多 5 則、每則約 10 秒」代表螢幕每分鐘最多約 30 則。200 人同時狂送時，系統會**誠實告知**多數人稍後再送，
  而不是假裝成功或把畫面塞爆。需要更多彈幕時可在控制面板調高「同時最多顯示」或改用全螢幕區域。
- 動畫由 Core Animation 在 WindowServer 端執行；CI 虛擬機無法量測實際投影的 FPS，流暢度請在實機目視確認。

## 3. 尚未驗證（需要你在實機確認）

| # | 項目 | 為什麼無法自動驗證 |
| --- | --- | --- |
| 1 | **Keynote 全螢幕播放**時彈幕是否在上方 | CI 機器沒有 Keynote；已用四種模擬方式驗證機制，但 Keynote 實際做法需實測 |
| 2 | PowerPoint 投影片放映 | 同上（CI 沒有 Office） |
| 3 | 預覽程式 / Acrobat 全螢幕 PDF | 同上 |
| 4 | **AirPlay 鏡像到 Apple TV → 投影機**是否同步顯示彈幕 | CI 沒有 Apple TV |
| 5 | 投影畫面上的 QR Code 能否被現場手機相機掃到 | 已驗證螢幕截圖可解碼；投影亮度、距離、角度需現場確認 |
| 6 | 真實 Wi-Fi 下的延遲、iPhone / Android 實機 | CI 為同一台機器的連線 |
| 7 | 全域快捷鍵在 Keynote 播放中有效、⇧⌘Q 不會觸發登出 | 需要實體鍵盤操作 |
| 8 | 第一次開啟的 Gatekeeper、防火牆、區域網路權限提示 | 需要你的 Mac |
| 9 | 長時間（例如 2 小時早會）穩定性 | CI 測試約 3 分鐘；已設計 App Nap 防護、斷線重連與連線逾時清理 |
| 10 | 投影畫面上的動畫流暢度與可讀性（亮、暗、照片背景） | 控制面板有即時預覽，但需現場目視 |

## 4. 實機驗收步驟（約 10 分鐘，會前做一次）

1. 安裝並打開 URBAN LIVE（見 README）。
2. 控制中心 →「螢幕鏡像」→ 選 Apple TV →「鏡像內建顯示器」。
3. 控制面板按「開始彈幕」→ 投影右下角出現 QR Code。
4. 用手機相機掃描投影上的 QR Code（實機項目 5）。
5. 輸入「URBAN 今天衝三件 🔥」→ 發送 → 手機顯示「已上大螢幕 ✓」，Mac 與投影都出現玻璃膠囊彈幕（項目 4、6）。
6. 控制面板 →「快捷鍵與進階」→「開啟相容性測試」→ 開始 60 秒測試 → 立刻切到 Keynote 按「播放」，
   觀察 Mac 與投影上的「🧪 相容性測試」彈幕（項目 1）。PowerPoint、PDF、瀏覽器同樣測一次（項目 2、3）。
7. 播放中點擊翻頁，確認滑鼠與鍵盤操作簡報正常（彈幕不擋操作）。
8. 播放中按 ⇧⌘P（暫停）、⇧⌘B（隱藏）、⇧⌘Q（QR Code）、⌃⌥⌘C（清空），確認生效且不會跳出登出對話框（項目 7）。
9. 按 Esc 結束播放，查看相容性測試結果；紀錄檔在 `~/Library/Logs/URBANLive/`。

若第 6 步看不到彈幕，依下一節的方案處理，並把紀錄檔傳給開發者。

## 5. Keynote 可行方案（依序嘗試）

| 方案 | 做法 | 說明 |
| --- | --- | --- |
| A（預設） | 直接全螢幕播放，視窗層級「自動」 | 自動偵測播放視窗層級並墊高；CI 已驗證四種全螢幕方式 |
| B | 控制面板 → 快捷鍵與進階 → 視窗層級「最高層級」 | 固定在 Shielding 之上，適用擷取整個螢幕的播放方式 |
| C | Keynote 設定 → 幻燈片秀，若有「允許 Mission Control、Dashboard 和其他 App 使用螢幕」之類選項，勾選 | 各版本名稱與是否存在不一定，以實際畫面為準 |
| D（保底，一定可行） | Keynote「播放 > 在視窗中播放」，把視窗放大填滿螢幕（按住 Option 點綠色按鈕；不要進全螢幕），並在「系統設定 → 桌面與 Dock」設定自動隱藏 Dock 與選單列 | 視窗化的幻燈片是一般視窗，彈幕必定在上方 |

PowerPoint 保底：「投影片放映 > 設定放映方式 >『觀眾自行瀏覽（視窗）』」。

## 6. 自己重跑自動測試（需要 macOS）

```bash
./scripts/build-app.sh                      # 打包
(cd tests && npm ci)                        # 測試工具
for i in $(seq 2 215); do sudo ifconfig lo0 alias 127.0.0.$i up; done   # 壓力測試用（可省略）
./scripts/smoke-test.sh                     # 全部整合測試，結果在 dist/smoke/
```

截圖類測試需要終端機的「螢幕錄製」權限；測試會暫時改動 `com.urban6699.live` 的設定並在結束時清除。
